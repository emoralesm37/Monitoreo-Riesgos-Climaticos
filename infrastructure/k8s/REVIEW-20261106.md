identidad/ACL por dispositivo, ID de mensaje estable, deduplicación de reenvíos
de hardware, capturedAt del dispositivo ni control de unidades en ese contrato.
La deduplicación Java por ID de lectura no evita que dos POST creen dos IDs SQL
y dos evaluaciones distintas. Las alertas requieren conservar el sobre persistido,
las reglas activas y la procedencia de la medición.

**Conclusión:** no integrar el commit tal cual como API física. La integración es
viable mediante un adaptador nuevo y probado dentro del modo compartido, con:

1. Identidad de puente/dispositivo y autorización para su sensor; no reutilizar
   sesiones humanas ni distribuir claves JWT a Arduino.
2. Contrato de mensaje con identificador idempotente, sensor, valor y capturedAt
   UTC; validar unidad/tipo, sensor activo, rango representable y desfase horario.
3. Restricción única de mensaje del dispositivo antes de crear la lectura y
   transacción de lectura + sobre. Esto requeriría una migración futura autorizada.
4. Reutilización de ReadingAlertDispatcher y deduplicación Java por medición/regla;
   reintentos con identidad autorizada sin persistir tokens de usuario.
5. Pruebas de 401/403, dispositivo ajeno, sensor inactivo, repetición y concurrencia,
   fallo/recuperación de alertas y regresión del POST manual y de reportes.

Estos puntos son diseño pendiente, no funcionalidad implementada ni una API lista
para hardware. No se modificaron Sensor Service, Auth, JWT o Gateway en ejecución.

## Bloqueos reales y límites para K3s

1. Capacidad: el presupuesto actual de Docker (6,62 GiB) no ofrece margen para
   los 5 024 MiB solicitados, control plane y los servicios locales que continúan
   activos. Elegir capacidad independiente antes de arrancar, sin detenerlos.
2. No hay k3d/k3s instalado como herramienta de trabajo; disponer de una VM/cliente
   verificado, versión/digest de K3s, contexto privado y red/almacenamiento nuevos.
3. Importar estas imágenes a containerd; Docker local no las hace accesibles por
   sí solo a K3s. No hay registro publicado ni imagen de release escaneada.
4. Provisión privada de Secrets, bases, esquemas y catálogos nuevos. Los Jobs SQL
   solo crean estructura en base vacía, no catálogos ni una app operativa con datos.
5. Probar PVC/UID/fsGroup con local-path real, CNI/NetworkPolicy, TLS/Ingress, DNS
   y readiness con las dependencias de ese laboratorio. No se demostró aquí.
6. OAuth: clientes y callbacks específicos del laboratorio, dominio HTTPS aceptado
   por proveedores y salida HTTPS de Auth. No se reutilizaron clientes privados.
7. Ingestión física: contrato/autorización/idempotencia/alertas siguen pendientes;
   no se resuelve activando alias del commit.

Antes de una release, resolver avisos observados: NU1902/NU1903 de Pkcs 9.0.11 y
dos avisos high en npm ci de runtime Auth; no se evaluó explotación ni se cambió
el lockfile. Angular construyó correctamente con 316,37 kB iniciales y advertencias
de SCSS de reportes/login y CommonJS de Leaflet. Estos avisos no impidieron las
construcciones; no equivalen a un K3s ya arrancado ni a un escaneo de release.
